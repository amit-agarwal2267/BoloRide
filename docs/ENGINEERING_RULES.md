# BoloRide — Engineering Rules

## 1. Plan first, implement second

Every coding task begins with a proposed implementation plan and waits for approval.

The plan should contain:
- goal
- affected files
- proposed types/interfaces
- database changes
- dependency changes
- environment changes
- test strategy
- risks/trade-offs

Do not make code changes while still discussing the plan.

## 2. Dependency management

Use `uv` exclusively.

When adding a package, explain why it is required and whether it is runtime or development-only.

Examples:

```bash
uv add fastapi
uv add sqlalchemy asyncpg
uv add --dev pytest pytest-asyncio ruff
```

Keep dependencies minimal. Do not add a framework when a small standard-library or existing-project solution is enough.

## 3. Runtime and testing

Run application commands inside Docker.

Examples:

```bash
docker compose exec boloride uv run pytest

docker compose exec boloride uv run alembic current

docker compose exec boloride uv run alembic upgrade head
```

If the container is not running, build/start it rather than falling back to host execution.

## 4. Configuration

All environment-specific configuration belongs in typed settings loaded from environment variables.

Rules:
- `.env` is never committed
- `.env.example` contains safe placeholders
- every newly required variable is added to `.env.example`
- fail fast for required secrets/configuration
- use explicit defaults only when the default is genuinely safe
- never silently substitute production-sensitive values

## 5. Database design checklist

Before proposing a migration, document:
- table purpose
- columns and SQL types
- primary key strategy
- foreign keys
- uniqueness constraints
- nullability
- check constraints
- timestamp semantics
- delete/update behavior
- expected read/write queries
- required indexes
- required PostgreSQL extensions

### Normalization

Prefer normalized data for the initial operational schema.

Avoid duplicating mutable user/location/provider data across tables unless there is an approved historical snapshot requirement.

If a ride needs immutable historical values, explicitly decide which values should be snapshotted and why.

### IDs

Choose ID types deliberately. Do not mix integer/UUID identifiers arbitrarily.

If UUIDs are chosen, decide whether they are generated by PostgreSQL or the application and configure extensions accordingly.

### Timestamps

Use timezone-aware timestamps for persisted events.

Distinguish intentionally between:
- created time
- updated time
- requested ride time
- booking/provider time

### Money

Do not store currency amounts as floating point.

Use fixed precision and an explicit currency representation.

### Phone numbers

Do not store phone numbers as numeric database types.

If persisted, normalize them as strings using a defined format and avoid exposing them directly in logs.

## 6. Migration rules

Migration history is part of the product.

Use small sequential revisions, for example:

```text
001_create_extensions.py
002_create_user_table.py
003_create_saved_place_table.py
004_create_driver_table.py
005_create_ride_table.py
006_create_offer_table.py
007_create_ride_indexes.py
```

Do not bundle unrelated schema changes in one revision.

A migration should be understandable without reading the entire application source.

Test migration upgrades inside Docker.

When practical, also test downgrade behavior for development migrations.

Never edit an already-applied shared migration merely to make history look cleaner. Add a new revision.

## 7. Index rules

Every non-obvious index must have an expected query pattern.

Examples of reasons an index may be justified:
- lookup user by normalized phone
- list recent rides for a user
- find active ride by user/status
- enforce provider booking id uniqueness

Do not index every foreign key/string automatically without considering workload and selectivity.

## 8. API design

Use typed request/response schemas.

API routes should:
- parse/validate transport input
- call a service
- map known errors to responses
- return structured schemas

Do not place SQL queries or significant business logic directly in route functions.

Health endpoints should remain simple and stable.

## 9. Error handling

Prefer explicit exception types over catching `Exception` everywhere.

Classify failures such as:
- validation/business rule failure
- provider timeout
- provider unavailable
- invalid provider response
- database failure
- configuration failure

Retry only transient failures.

Do not retry:
- invalid user input
- failed business-rule validation
- authentication/authorization errors
- deterministic schema errors

## 10. Retries and idempotency

Booking is a side-effecting operation.

Any retry policy must avoid duplicate rides.

Before implementing booking retries, define an idempotency strategy. Do not simply retry `create_ride()` after a timeout without knowing whether the provider created the ride.

## 11. Logging

Use structured logs.

Prefer event names over sentence-style log messages.

Example:

```json
{
  "event": "location_resolution_completed",
  "session_id": "...",
  "provider": "google_maps",
  "candidate_count": 3,
  "duration_ms": 184
}
```

Redact or avoid PII by default.

## 12. Tests

Write tests around behavior, not file coverage.

### Unit

Best for:
- domain policies
- service validation
- tool input mapping
- router/fallback logic
- deterministic evals

### Integration

Best for:
- PostgreSQL repositories
- Alembic migration chain
- Langfuse integration
- map adapter
- voice pipeline boundaries

### Contract

Best for provider interfaces so that mock and future production adapters satisfy the same expectations.

## 13. External integrations

Wrap vendor SDKs.

Never let vendor response objects leak through all layers of the codebase.

Translate them into BoloRide domain/application types.

## 14. Prompt management

Prompt source order:

```text
Langfuse prompt
    ↓ unavailable
local fallback prompt
```

Do not silently use a fallback without logging/tracing that fallback was used.

Prompt changes should not require rebuilding the BoloRide application image.

## 15. Security mindset

This is a hackathon project, but avoid security claims the implementation does not support.

Never commit:
- API keys
- provider tokens
- database passwords
- Langfuse secret keys

Do not treat caller phone-number matching as high-assurance authentication.

## 16. Keep the implementation explainable

Prefer a small architecture that can be defended in an interview or hackathon review over unnecessary abstraction.

Do not add:
- a new service
- a queue
- Redis
- LangGraph
- an LLM gateway
- a second database
- a microservice

unless there is a concrete requirement and the trade-off has been discussed first.
